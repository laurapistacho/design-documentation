11:Ted5,# Loading & Skeleton States

Loading feedback tells users the system is working. ReviewPro uses skeleton screens as the primary loading pattern, not spinners.

## Loading Hierarchy

| Duration | Pattern | Usage |
|----------|---------|-------|
| < 300ms | No indicator | Instant transitions, local state changes |
| 300ms - 2s | Skeleton | Page loads, data fetching, tab switches |
| > 2s | Skeleton + progress text | Long operations (report generation, export) |
| Indefinite | Spinner (rare) | File uploads, background processing |

## Skeleton Pattern

Skeletons mirror the layout of the content they replace. Every data region has a skeleton variant that matches its final shape.

### Rules

1. **Shape matches content.** Text lines = gray rectangles at text height. Avatars = circles. Cards = card-shaped blocks.
2. **Animate with shimmer.** Left-to-right gradient sweep, 1.5s cycle.
3. **Preserve layout.** Skeleton occupies the exact same space as loaded content (no layout shift).
4. **Group by data source.** Elements that load together skeletonize together.

### Component Skeleton States

Many components have a built-in `Skeleton` state variant:

| Component | Skeleton behavior |
|-----------|------------------|
| Button | Gray rounded rectangle, no text |
| IconButton | Gray circle |
| Chip | Gray pill shape |
| Table Row | Gray bars for each cell |
| Card/Tile | Gray header bar + body lines |
| Avatar | Gray circle |
| Toggle | Gray track + handle |

## Where to Use Skeletons

| Context | Skeleton scope |
|---------|---------------|
| Initial page load | Full page content (below header) |
| Tab switch | Tab content area only |
| Table data refresh | Table body rows (keep header visible) |
| Card content | Card body (keep card frame visible) |
| Sidebar panel | Panel content (keep rail visible) |
| Drawer open | Drawer content area |

## Where NOT to Use Skeletons

- Navigation chrome (TopNav, SideNav) — these are static, never skeleton
- Already-loaded content on the same page — don't re-skeleton
- Interactive controls (buttons, tabs) — they should remain responsive
- Filters/search — user should be able to type immediately

## Shimmer Animation

```css
@keyframes shimmer {
  0% { background-position: -200px 0; }
  100% { background-position: calc(200px + 100%) 0; }
}

.skeleton {
  background: linear-gradient(
    90deg,
    #F1F1F1 25%,    /* neutral_08 */
    #E4E4E4 50%,    /* neutral_10 */
    #F1F1F1 75%     /* neutral_08 */
  );
  background-size: 200px 100%;
  animation: shimmer 1.5s infinite;
  border-radius: 4px;
}
```

## Transition Behavior

- **Appear:** skeleton shows immediately (no fade-in delay)
- **Disappear:** content fades in over 200ms, replacing skeleton
- **Partial load:** skeleton for unloaded regions, real content for loaded ones (progressive)

## Inline Loading (Circular Progress)

Used only for:
- Buttons in loading state (spinner replaces icon, text stays)
- Autocomplete search (spinner in the right icon position)
- Upload progress (circular with percentage)

Never use a full-page centered spinner.

## Do / Don't

- Do: show skeletons for all data-dependent content
- Don't: show a blank page while loading
- Do: keep interactive elements (nav, filters) responsive during load
- Don't: block the entire page with a loading overlay
- Do: match skeleton shapes to content shapes precisely
- Don't: use generic gray blocks that don't match the layout
- Do: animate with shimmer (indicates progress, not just empty)
- Don't: use spinners for page loads (spinners are for actions, not content)

## Implementation

**Code:** `@reviewpro/ui-components` > `Skeleton` (via MUI), `CircularProgress`, `LinearProgress`, `Loader`
**States:** Most components expose a `Skeleton` variant in Figma (check component variants)
